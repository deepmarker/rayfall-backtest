# Backtester correctness, performance and data-loading audit

Date: 2026-10-21. Engine revision: `1a44b6975`; Rayforce
`2.10.0.r206.g64645998`; NautilusTrader `1.230.0`; Arrow `25.0.0`.
Machine: sita, Ryzen AI 7 350, 16 logical CPUs, 46 GiB RAM. See the
raw results and scripts (historical local output, not versioned).

The existing valid-input checks pass and the measured performance targets
are met. Profiling identifies an upstream symbol-lock bottleneck. A reliable
Nautilus backtest comparison first needs a validated common data adapter.
No accounting-engine behavior was changed by this audit.

## Correctness

`make test test-run fmt-check` passes: six fixtures, scalar/vector kernel
and view/features equivalence, future-data perturbation checks, and two
byte-identical runs of both example strategies (18 output files each).

The new `test/oracle.py`, included in `make test`, checks 50 seeded scenarios
against independent Python integer accounting. Each scenario has three
instruments and 16 steps, shuffled input, missing bars, missing targets,
rejections, partial closes, fee rounding and cost-basis rounding. All numeric
fill, position and equity fields agree. It uses the REJECT policy with limits
that do not bind; SCALE and portfolio limits retain their separate fixtures.
This adds independent evidence beyond comparing two closely related kernels.
It does not establish correctness for every strategy or execution model.

Input validation has a concrete gap, reproduced by
the config probes (historical local output, not versioned):

- Null bar times and multipliers are rejected.
- A null or missing `fee_ppm` is accepted by `bt_run`; the identity check
  subsequently fails. This contradicts the contract that missing/invalid
  configuration keys raise at input validation.
- Negative fees are accepted and accounting treats them as rebates. Either
  prohibit them for this fee model or explicitly specify and test rebates.

`bt_metrics` also assumes daily observations (`365` periods/year) regardless
of `bt.period`. The hourly benchmark is a cost measurement, as its existing
comments specify; its annualized metrics should not be used as hourly
performance statistics. Generalizing reports requires duration-aware
annualization and handling zero volatility and empty evaluation windows.

## Performance

Synthetic snapshots: 100 instruments, 1096 days, 109,600 daily or 2,630,400
hourly rows. Whole-process times below are hyperfine means from three runs
after one warm-up. Phase timings and peak RSS come from separate instrumented
runs. Page cache is warm; the machine was not exclusively reserved. These are
new measurements, not comparisons with the older Intel machine's results.

| Workload | Whole process | Peak RSS |
|---|---:|---:|
| Daily kernel | 0.120 s | 188 MiB |
| Daily hold/view construction | 0.587 s | 194 MiB |
| Daily momentum on view | 1.383 s | 221 MiB |
| Daily momentum with features | 0.222 s | 223 MiB |
| Daily trend on view | 1.425 s | 225 MiB |
| Hourly kernel | 3.209 s | 1085 MiB |
| Hourly momentum with features | 5.365 s | 1851 MiB |
| Daily scalar-reference kernel | 0.392 s | 188 MiB |

Features momentum meets the daily <1 s and hourly <30 s targets. It is
6.2 times faster than the daily view implementation. The vector kernel is
3.3 times faster than the scalar kernel in the daily kernel-only workload.

For hourly features momentum, the instrumented phases are CSV load 85 ms,
run 3985 ms (including preparation 182 ms), and checks 1255 ms. Strategy
callbacks themselves consume 30 ms. Loading is a small part of this workload;
view construction, sorting, record handling and checks deserve attention
before optimizing arithmetic in strategy callbacks.

## Frame-pointer profiles

The packaged release omits frame pointers. For valid `fp` stacks, a clean
archive of upstream `64645998` was built with its release optimization flags
plus `-g -fno-omit-frame-pointer -mno-omit-leaf-frame-pointer`. This isolated
build leaves the upstream checkout and installed binary untouched. Its six
fixtures and kernel equivalence pass. Build identity and flags are recorded
in environment.json (historical local output, not versioned).

Profiles use `perf record -F 999 -e cycles:u --call-graph fp`. No samples were
lost. Raw perf files and the binary are under ignored `data/audit-profiles/`
and `data/audit-rayforce-fp/`; text reports are retained in the results tree.
reproduce.sh (historical local output, not versioned) rebuilds
and records the three workloads after the synthetic snapshots exist.

| Profile | `ray_sym_str` self cycles | Other notable self cycles |
|---|---:|---|
| Hourly kernel, 21,555 samples | 84.16% | CSV parse 1.65%, free 1.46% |
| Hourly features momentum, 31,605 samples | 61.54% | gather 7.26%, binary operations 4.31% |
| Daily view momentum, 6103 samples | 12.78% | expression loads 21.94%, row selection 10.23%, gather 9.05% |

The hourly caller chain is `sorted_check_fn` -> `ray_sym_str` -> `sym_lock`.
The annotated assembly places most samples inside the spin loop. The generic
already-sorted `(timestamp, symbol)` scan compares symbol strings within each
timestamp group and acquires the global symbol lock for each lookup.

The isolated reproducer (historical local output, not versioned)
checks 2,630,400 already-sorted rows. Each cell is the median of three
fresh-process measurements, excluding data loading:

| Key representation | `RAYFORCE_CORES=1` | `RAYFORCE_CORES=16` |
|---|---:|---:|
| Timestamp and symbol | 80.8 ms | 1229.6 ms |
| Timestamp and lexical integer rank (diagnostic control) | 17.1 ms | 13.7 ms |

The symbol scan is 15 times slower at setting 16 than at 1. A separate,
single whole-kernel probe at setting 1 reduced its internal run phase from
roughly 3.1 s to 2.1 s. Sampled CPU percentages include all threads and cannot
be interpreted as percentages of wall time or as a promised speedup.

The upstream candidate is to prepare stable symbol strings or lexical ranks
once per key before dispatch, preserving symbol domains, null ordering and
lifetime guarantees. Rayforce already has a read-only symbol-table borrow
facility, but it requires an explicit no-concurrent-interning contract.
Removing the lock globally would be unsafe. No such workaround was added to
the backtester. See the [upstream issue #933](https://github.com/RayforceDB/rayforce/issues/933)
and its [local report](upstream/rayforce-sorted-symbol-spinlock.md).

## NautilusTrader data loading

This comparison uses the existing local DBN files offline, with no download
or API changes. Both paths consume the same record payloads. For Rayforce,
the installed official `dbn` CLI produces integer CSV, then Arrow writes
Snappy Parquet with integer prices and nanosecond timestamps. This is an
explicitly measured derived conversion, not a direct DBN reader. It avoids
the existing sample Parquet's floating-point prices.

Nautilus decodes DBN directly to Cython or Rust objects, imports those objects
into its own Parquet catalog, and queries that catalog back to Cython
objects. Rayforce reads columnar tables or opens a native splayed cache.
These are different representations and amounts of work: this is a loading
path comparison, not an execution-engine speed contest.

The configured probes explicitly set diagnostic instrument IDs and eight
price decimals. Production instruments still need definition-derived venue,
price and quantity units. Nautilus's default bar timestamps are on close;
`bars_timestamp_on_close=False` aligns `ts_event` with the backtester's bar-open
keys while retaining close-time availability in `ts_init`.
[Official timestamp convention](https://nautilustrader.io/docs/latest/integrations/databento/).

### BTCUSDT trades: 726,611 records

Repeated decode/read phases use the median of three fresh-process runs;
conversion/import phases are single measurements. Memory includes the
process and its imported dependencies, not just the loaded records.

| Path | Phase time | Peak RSS |
|---|---:|---:|
| Nautilus DBN -> Cython objects | 165 ms | 636 MiB |
| Nautilus DBN -> Rust objects | 129 ms | 522 MiB |
| Nautilus catalog -> Cython objects | 116 ms | 446 MiB |
| Rayforce derived Parquet -> full table | 80.3 ms | 297 MiB |
| Rayforce native open + two-column checksum scan | 0.20 + 2.37 ms | 27 MiB |

Native open is lazy. The checksum scans price remainders and sizes and checks
timestamp bounds; it does not construct objects or touch every other column.
Its result must not be described as fully materializing the dataset in
0.20 ms. Native files occupy 72.7 MB versus 12.0 MB for derived Parquet and
9.2 MB for the Nautilus catalog (decimal units).

One-time DBN -> integer CSV -> Parquet costs 233 + 199 ms. Native import costs
122 ms. Nautilus Cython catalog import costs 174 ms decode + 1287 ms write;
the Rust path costs 125 + 741 ms. Python dependency import/startup is excluded
from these phase times; the raw worker measurements also retain its overhead.
Cold storage reads and dataset sizes above this sample were not measured.

**The trades path is not semantically ready.** The current default
`nautitest/src/ingest.py` fails to decode an instrument ID. Explicit instrument
and precision overrides allow decoding, but every resulting trade has
`ts_event=0` and `ts_init=0`, while source event times are in January 2025 and
`ts_recv=0`. The catalog consequently returns zero records for the source-day
query. The full value comparison finds matching prices and sizes but
726,611 event-time mismatches. These timings describe a compatibility probe,
not a correct production-ready trades pipeline.

### Bar samples

The MORPHOUSDT sample has 551 valid daily bars. Configured Nautilus decode
costs about 1.2 ms and catalog query 3.7 ms; Rayforce Parquet read costs
0.69 ms. At this size format tuning is secondary to Python startup and
correct semantics. Every decoded OHLC, volume and open timestamp matches the
canonical DBN columns with the explicit configuration.

The AAVE sample has 56 invalid OHLC rows among 882 records: for example,
2024-01-03 has open 110.39, high 99.99 and low 100.00. Nautilus's configured
bar decoder aborts on `high >= open`; silently repairing this would conceal
a source-data defect. The backtester currently only consumes `o` and `c`,
so a shared adapter must validate the complete OHLC tuple before either path.

The default loaders also interpret publisher 4 as `XPSX`, and fail to resolve
price precision for both bar samples. Resolve venue identity and precision
from a validated provider/definition mapping; do not rely on the diagnostic
overrides as an ingestion design. File hashes, failures and full field
comparisons are retained in `loading/verification.json` and
`loading/semantic-comparison.json` in the results directory.

## Next steps

1. Harden scalar configuration validation, particularly required/non-null
   fees, and decide whether rebates are supported. Add negative controls to
   the independent accounting tests; make report annualization period-aware
   before using hourly strategy statistics.
2. Fix the sortedness-check symbol contention upstream, with the small
   reproducer and profiles, then rerun the same benchmarks. Profile the
   remaining gather/join/check costs after that change. Porting trend to
   features mode remains the clearest strategy-side optimization.
3. Implement one strict shared DBN bar adapter: exact price/quantity units,
   validated OHLC and symbol/venue mapping, explicit open and availability
   timestamps, and pinned source checksums. Resolve the trades timestamp
   issue separately; do not use the current trades catalog for parity.
4. Run the same buy-and-hold strategy in both engines on valid shared bars,
   reconcile fills, fees and every equity boundary, and document execution
   differences. Nautilus strategy/engine parity was not tested here:
   `nautitest` currently implements ingestion, not that backtest.

## Reproduce

From `backtest`, run `make test test-run fmt-check`, or
`make test-oracle` for the independent oracle alone. The measured grid uses
`bench/run.sh` with `HF_RUNS=3 HF_LIMIT_S=10`, size `100`, daily modes
`kernel hold xsmom xsmomf trend`, and hourly modes `kernel xsmomf`.
The reference daily run uses `KERNEL=ref/bt_ref.rfl` and modes `kernel xsmom`.
The environment files retain full commands' settings and binary identity.

From the dm root, run the saved `loading/run.py` with Python 3, and
`loading/verify.py` and `loading/compare_values.py` with
`nautitest/.venv/bin/python`. Their directory is
`backtest/bench/results/2026-10-21-sita/loading/`.
All generated datasets and raw perf binaries live under ignored
`backtest/data/`. The measurements require the local DBN samples;
no API credentials are used.
